# 장애격리 전체 그림 (지금까지 배운 것 기준)

> 목적: "장애격리"로 따로 정리된 노트는 없었지만, 그 목적에 해당하는 메커니즘은 여러 Day에
> 흩어져 있었다. 이 노트는 그것들을 **범위가 작은 것 → 큰 것** 순서로 이어붙여 하나의
> 그림으로 정리한다. Namespace/NetworkPolicy/taint/서킷 브레이커/멀티 AZ는 아직 안 배운
> 내용이라 이 노트에는 없다 (맨 아래 "아직 다루지 않은 것" 참고).

## 격리의 층위 — 작은 범위 → 큰 범위

### 1. 프로세스/컨테이너 레벨 — namespace + cgroup
가장 근본적인 층. 컨테이너 하나가 죽거나 이상 동작해도 **같은 호스트의 다른 컨테이너에
직접 번지지 않는** 이유는 커널의 namespace(시야 격리: 자기 파일시스템/네트워크/프로세스
목록만 보임)와 cgroup(자원 사용량 제한) 덕분이다. 모든 격리의 토대.
→ [Day 1 §1](day01-docker-basics.md), [Day 5](day05-docker-basics-review.md)

### 2. 자원 레벨 — requests/limits → cgroup 매핑
한 노드 위 여러 컨테이너가 있을 때, **한 컨테이너의 자원 폭주가 다른 컨테이너의 몫까지
빼앗지 않도록** 커널이 강제한다. CPU는 압축 가능 자원이라 한도 초과 시 스로틀링(느려짐,
안 죽음)만 되고, 메모리는 압축 불가능이라 한도 초과 시 그 컨테이너만 OOM Kill된다 — **그
컨테이너 안에서 격리가 끝나고 다른 컨테이너는 안 건드림.**
→ [Day 3 §2](day03-hpa-scheduling.md), [lab-cgroup-verification.md](lab-cgroup-verification.md)
(`cpu.max`, `memory.max` 실측 확인 완료)

### 3. 파드 레벨 — readiness probe
한 파드가 일시적으로 문제(느린 DB 연결 등)를 겪어도, **그 파드 하나만 트래픽에서 조용히
빠지고** 다른 파드는 정상 서비스를 계속한다. 재시작도 안 하고 다른 파드에 영향도 없다 —
"고장난 하나 때문에 전체가 흔들리지 않게"의 가장 작은 단위 실현.
→ [Day 7 §4](day07-docker-k8s-bridge.md) (실습: 404 126회 실패에도 RESTARTS 0)

### 4. 노드 레벨 — QoS 클래스와 축출 순위
노드 전체가 메모리 압박을 받을 때, **누구를 먼저 희생시킬지**를 자원 선언 방식으로 미리
정해둔다. 정직하게(requests==limits) 선언한 파드는 끝까지 보호되고, 아무것도 선언 안 한
파드가 먼저 축출된다 — "한 노드의 위기가 전체 워크로드에 균등하게 번지지 않도록" 우선순위를
매기는 것.
→ [Day 7 §6](day07-docker-k8s-bridge.md) (QoS Guaranteed/Burstable/BestEffort 자동 판정 실습)

### 5. 배포(버전) 레벨 — 롤링 업데이트 안전장치
새 버전이 통째로 고장나도(`ImagePullBackOff` 등), **그 실패가 사용자에게 번지지 않도록**
`maxUnavailable: 0` + readiness probe가 옛 버전을 붙잡아둔다. 배포 실패의 블라스트 반경이
"롤아웃이 멈춘 상태"로 국한되고, 서비스 자체는 무중단.
→ [Day 7 §5](day07-docker-k8s-bridge.md) (실습: 고장 이미지 배포에도 14분간 무중단)

### 6. 컨트롤 플레인 레벨 — 컴포넌트 분리
kube-apiserver, scheduler, controller-manager, etcd, kubelet을 하나로 합치지 않고
**따로 분리해서**, 한 컴포넌트가 죽어도 다른 컴포넌트는 계속 동작한다 (예: scheduler가
잠깐 죽어도 이미 떠 있는 파드는 계속 서비스됨). 다만 이 부분은 Day 2에서 한 줄로만
언급됐고 깊게 다루진 않았다.
→ [Day 2 §2](day02-kubernetes-basics.md)

### 7. 네트워크 레벨 — 네트워크 간 격리 (성격이 조금 다름)
Docker 커스텀 네트워크나 Compose 프로젝트별 네트워크는 원래 "이름으로 통신하기 위한"
장치였지만, 부수적으로 **다른 네트워크의 트래픽이 안 섞이는** 보안/조직적 격리도 제공한다.
장애 전파 방지라기보다 침투/혼선 방지에 가깝지만, "범위를 나눈다"는 점에서 같은 계보.
→ [Day 6](day06-dockerfile-networking.md)

## 정리 — 각 층위가 막는 것

| 층위 | 막는 것 |
|---|---|
| 프로세스/컨테이너 (namespace+cgroup) | 한 컨테이너의 크래시가 다른 컨테이너로 직접 전염 |
| 자원 (requests/limits) | 한 컨테이너의 자원 폭주가 이웃 컨테이너의 몫을 빼앗음 |
| 파드 (readiness) | 파드 하나의 일시적 문제가 전체 트래픽에 영향 |
| 노드 (QoS) | 노드 자원 위기가 모든 워크로드에 무차별적으로 번짐 |
| 배포 (rolling update) | 고장난 새 버전이 전체 사용자에게 노출 |
| 컨트롤 플레인 (컴포넌트 분리) | 관리 기능 하나의 장애가 클러스터 전체 마비로 확산 |

> **면접 답변**: "장애격리는 한 계층에서 끝나는 게 아니라, 컨테이너 → 자원 → 파드 → 노드 →
> 배포 → 컨트롤 플레인까지 각 층위마다 별도 메커니즘으로 반경을 좁혀둡니다. 예를 들어
> readiness probe는 파드 하나의 문제를 트래픽 계층에서 격리하고, QoS 클래스는 노드
> 자원 위기 시 축출 순위로 격리하며, maxUnavailable과 readiness의 조합은 배포 실패를
> 롤아웃 자체에 가둬 사용자에게 전파되지 않게 합니다. 각 메커니즘은 서로 다른 장애
> 시나리오를 막기 때문에 하나만으로는 충분하지 않습니다."
