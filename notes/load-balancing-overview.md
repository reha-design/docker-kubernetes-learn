# 부하분산 전체 그림 — 사용자 요청부터 DB까지

> 목적: 지금까지 배운 kube-proxy/Service/Ingress/canary는 실제 서비스가 사용자 요청을
> 처리하는 전체 경로 중 **한 구간씩**이었다. 이 노트는 그 구간들을 실제 요청이 흘러가는
> 순서대로 이어붙여서, "부하분산은 하나의 장치가 아니라 경계마다 반복 적용되는 개념"이라는
> 큰 그림을 정리한다.

## 요청이 지나가는 전체 경로 (바깥 → 안쪽)

### 1. DNS / GeoDNS
가장 바깥, 가장 거친 단위의 분산. 사용자가 도메인을 조회하면 **지역별로 다른 IP**를
돌려줄 수 있다(한국 사용자→서울 리전, 미국 사용자→버지니아 리전). 요청 단위가 아니라
"어느 대륙/리전으로 보낼지"를 정하는 것이라 실시간 반응성은 없다.

### 2. CDN 엣지 (Cloudflare, CloudFront 등)
정적 자산은 물론 API 응답 캐싱까지, **사용자와 가장 가까운 엣지 서버**가 먼저 처리한다.
캐시에 있으면 origin(우리 서버)까지 아예 안 온다 — 부하 자체를 origin에서 치워버리는
것도 넓은 의미의 부하분산이다.

### 3. 클라우드 L4/L7 로드밸런서 (AWS ALB/NLB, GCP LB 등)
클러스터 **바깥**에서 실제 트래픽을 받는 진입점.
- **L4(전송 계층)**: IP+포트만 보고 TCP 연결을 분산. HTTP 내용은 모름, 빠름.
- **L7(애플리케이션 계층)**: HTTP를 이해해서 path/header/도메인 기준 라우팅, TLS 종료까지
  담당. [Day 2 §8의 Ingress](day02-kubernetes-basics.md)가 바로 이 L7 계층의 K8s 버전 —
  클라우드 L7 LB가 트래픽을 받아 클러스터의 Ingress 컨트롤러(nginx 등)로 넘기는 구조가 흔하다.

### 4. Kubernetes 내부 (Service / kube-proxy / EndpointSlice)
Ingress → **Service(ClusterIP)** → **kube-proxy**가 심어둔 iptables/IPVS 규칙 →
**EndpointSlice**에 등록된 Ready 파드 중 하나로 전달. iptables 모드는 사실상 **랜덤
선택**, IPVS 모드는 라운드로빈 등 실제 알고리즘 선택이 가능하다 — 자세한 동작 원리와
"EndpointSlice가 readiness로 거르고 kube-proxy는 그 결과를 반영할 뿐"이라는 구분은
[Day 2 §5](day02-kubernetes-basics.md#5-service--왜-필요한가)에 정리돼 있다.

### 5. 서비스 메시 (Istio, Linkerd — 선택적, 대규모에서 흔함)
각 파드 옆에 **사이드카 프록시**(Envoy 등)를 붙여 kube-proxy보다 정교한 분산을 한다:
최소 연결 수 기준 라우팅, 재시도, 서킷 브레이커. [Day 7 canary 실습](day07-docker-k8s-bridge.md#5-배포-전략--rolling-update-파라미터-롤백-blue-greencanary)에서
"파드 개수 비율" 방식이 이론값(80:20)과 실측값(75:25)이 갈렸던 게 바로 이 계층이
필요한 이유 — 서비스 메시는 파드 개수가 아니라 **실제 트래픽 %**로 정밀하게 나눈다.

### 6. 클라이언트 사이드 로드밸런싱 (gRPC, 마이크로서비스 간 통신)
서버 간 통신에서는 아예 **클라이언트가 여러 백엔드 주소를 직접 알고 분산**하기도 한다
(중간 LB를 안 거쳐 홉이 줄어듦). Netflix의 Eureka+Ribbon 패턴이 대표적 예시.

### 7. 데이터베이스 계층
파드가 아무리 잘 분산돼도 전부 **같은 DB 하나**를 때리면 결국 거기서 병목이 난다.
- **읽기 복제본(read replica)** + 라우터(PgBouncer, RDS Proxy 등)로 읽기 쿼리를 분산
- 쓰기는 일관성 때문에 primary 하나로 집중

## 왜 한 겹이 아니라 여러 겹인가

| 계층 | 해결하는 문제 |
|---|---|
| DNS/CDN | 지리적으로 먼 요청을 origin까지 안 오게 |
| 클라우드 LB | 클러스터 바깥에서 여러 노드로 진입점 분산 |
| Ingress | 클러스터 안에서 도메인/경로별 라우팅 |
| Service/kube-proxy | 같은 앱의 여러 파드 중 하나로 분산 + Ready 필터링 |
| 서비스 메시 | 더 정교한 알고리즘, 세밀한 트래픽 비율 제어 |
| DB 프록시 | 최종 병목인 DB로의 읽기 부하 분산 |

각 계층은 **서로 다른 경계**(리전 간, 클러스터 안팎, 파드 간, DB 앞)에서 발생하는
서로 다른 문제를 풀기 때문에, 하나로 통합할 수 없고 중첩해서 쌓인다.

> **면접 답변**: "부하분산은 한 가지 기술이 아니라 요청이 지나가는 경계마다 반복
> 적용되는 개념입니다. 바깥에서부터 DNS/CDN, 클라우드 L4/L7 로드밸런서, 클러스터
> 안에서는 Ingress와 Service(kube-proxy), 더 정교한 제어가 필요하면 서비스 메시,
> 그리고 최종적으로 DB 앞의 읽기 복제본 라우터까지 이어집니다. 제가 직접 실측한 건
> Service/kube-proxy 계층(EndpointSlice 기반 Ready 필터링, iptables/IPVS 모드)과
> Ingress, 그리고 canary에서 파드 개수 비율 방식의 한계(이론 80:20 vs 실측 75:25)까지고,
> 그 바깥 계층(클라우드 LB, CDN, 서비스 메시)은 개념적으로 이해하고 있습니다."
