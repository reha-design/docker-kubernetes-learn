## 복습 결과 요약
문답 방식으로 day01~02 내용을 점검한 결과:
### 교정된 부분 (재복습 필요)
- **limits 초과를 Pending으로 답한 오류** — limits 초과는 런타임에 커널이 죽이는 **OOMKilled**. Pending은 실행 전 스케줄링 실패.
  - 구분 요령: **"컨테이너가 실행되긴 했나?"** 한 가지만 물으면 됨. 실행 전 = 스케줄러/requests 문제(Pending), 실행 후 = 커널/limits 문제(OOMKilled)
- **requests/limits 역할 분리가 힌트로도 안 떠올랐음** — requests = 스케줄러의 사전 예약 장부, limits = 커널의 사후 단속선. overcommit(limits 합계 > 노드 용량)이 허용되는 이유: limits는 배치 결정에 안 쓰이니까.
- Pending 파드는 `Node: <none>` — 배치된 노드가 없으니 **이미지 pull조차 발생하지 않음** (pull은 배치된 노드의 kubelet이 하는 일)
### 안정적이었던 부분
- HPA가 max까지 안 늘어나는 이유(공식 계산 결과가 현재 replica 이하), max 도달 시 상태가 장애가 아닌 설계된 상한선이라는 것, 운영 대응(max 상향 / Cluster Autoscaler / alert)

## Docker 기초: 이미지 vs 컨테이너
### 컨테이너가 풀려는 문제
"내 컴퓨터에선 되는데요?" — 코드만 옮기면 파이썬 버전, 라이브러리, OS 설정 등 **환경**이 달라 안 돌아감. 컨테이너 = 앱 + 실행 환경 전체를 하나의 상자로 묶어 어디서든 똑같이 동작하게 만드는 기술.
### 이미지 vs 컨테이너 (가장 기본이 되는 구분)
| | 이미지 (Image) | 컨테이너 (Container) |
|---|---|---|
| 정체 | 앱+환경을 묶은 읽기 전용 **설계도/틀** | 이미지를 **실행한 인스턴스** |
| 비유 | 붕어빵 틀 | 구워진 붕어빵 |
| 관계 | 이미지 1개로 컨테이너 여러 개 생성 가능 | |
- `kubectl run ... --image=busybox` = "busybox라는 틀로 컨테이너를 구워라"
- HPA가 replica를 늘릴 때 동일한 파드가 즉시 복제될 수 있는 것도 이미지 덕분
- **Pull = 틀(이미지)을 레지스트리(창고)에서 노드로 가져오는 행위.** 컨테이너가 아니라 이미지를 가져오는 것.
- 용어 주의: "이미지 실행 시간"(X) → 이미지는 실행 주체가 아님. "앱/컨테이너 시작 시간"(O)
### 정상적인 파드 시작 3단계
1. **스케줄러**가 노드 배치 결정 (requests 장부 확인)
2. 그 노드의 **kubelet이 이미지 pull** (틀 가져오기)
3. 이미지로 **컨테이너 생성/시작** (붕어빵 굽기)
---
## 파드가 안 뜨는 두 상황
| 구분 | (a) Pending + FailedScheduling | (b) ErrImagePull |
|---|---|---|
| 실패 단계 | 1단계 (스케줄링) | 2단계 (이미지 pull) |
| 배치 여부 | `Node: <none>` — 배치 실패 | 배치는 성공 (`Node:`에 노드명 있음) |
| 손볼 곳 | requests 낮추기 / 노드 자원 확충(CA) | 이미지 이름·태그 오타, 레지스트리 접근(네트워크, private 인증) |
| 확인 | `describe pod` → FailedScheduling + `describe node` Allocated resources | `describe pod` → 이미지 관련 Events |
같은 "파드가 안 뜬다"라도 **실패 단계에 따라 보는 곳과 고치는 곳이 완전히 다름** — 트러블슈팅 질문의 뼈대.

## 컨테이너 vs 가상머신(VM)
### 구조 비교
```
[VM]                              [컨테이너]
앱 + 라이브러리                     앱 + 라이브러리
게스트 OS (커널 포함) ← VM마다 복제   (커널 없음!)
하이퍼바이저                        도커 엔진
호스트 OS                          호스트 OS ← 커널 하나를 모두가 공유
하드웨어                           하드웨어
```
- **VM**: 인스턴스마다 게스트 OS 통째로 → 수 GB, 시작 = OS 부팅(수십 초)
- **컨테이너**: 호스트 커널 공유, 이미지엔 앱+라이브러리만 → 수십 MB, 시작 = 프로세스 실행(수 초)
### 격리의 실체 (커널 기능 2가지)
- **namespace**: 프로세스의 **시야** 격리 — 자기 파일시스템/네트워크/프로세스 목록만 보임
- **cgroup**: 프로세스의 **자원 사용량** 제한 — K8s limits를 집행하는 게 바로 이것 (OOMKilled의 주체)
→ 컨테이너 = "namespace로 눈을 가리고 cgroup으로 손발을 묶은, 커널 위의 일반 프로세스". 별도 OS가 아님.
### 커널 공유의 제약
- 이미지에는 커널이 없음 → 컨테이너는 **호스트와 같은 커널 계열만 실행 가능**
- 리눅스 서버에서 Windows 컨테이너 직접 실행 불가 (시스템 호출이 안 통함)
- 그런데 Windows에서 리눅스 컨테이너가 도는 이유 = **WSL2**: Windows가 경량 VM으로 진짜 리눅스 커널을 돌리고, Docker는 그 위에서 동작
  ```
  Windows → WSL2(리눅스 커널을 가진 경량 VM) → Docker → 리눅스 컨테이너들
  ```

## 면접 답변 템플릿
### Q. 이미지와 컨테이너의 차이는?
> "이미지는 앱과 실행 환경을 묶은 읽기 전용 템플릿이고, 컨테이너는 그 이미지를 실행한 인스턴스입니다. 클래스와 인스턴스 관계처럼 하나의 이미지로 컨테이너를 여러 개 띄울 수 있고, 쿠버네티스에서 HPA가 replica를 빠르게 늘릴 수 있는 것도 이 구조 덕분입니다."
### Q. 컨테이너가 VM보다 가벼운 이유는?
> "VM은 인스턴스마다 게스트 OS를 통째로 올리기 때문에 커널을 포함해 수 GB를 차지하고, 시작할 때마다 OS 부팅 시간이 듭니다. 반면 컨테이너는 호스트 OS의 커널을 공유하고 이미지에는 앱과 라이브러리만 담기 때문에 용량이 수십 MB 수준이고, 시작도 부팅이 아니라 프로세스 실행이라 수 초면 됩니다. 격리는 커널의 namespace(가시성)와 cgroup(자원 제한)으로 이뤄집니다."
### Q. 리눅스 서버에서 Windows 컨테이너를 띄울 수 있나요?
> "안 됩니다. 컨테이너 이미지에는 커널이 포함되지 않고 호스트 커널을 공유하는 구조라, 호스트와 같은 커널 계열만 실행할 수 있습니다. Windows에서 리눅스 컨테이너가 도는 것은 WSL2가 경량 VM으로 리눅스 커널을 제공해주기 때문입니다."
### Q. Pending과 ErrImagePull의 차이는?
> "파드 시작은 스케줄링 → 이미지 pull → 컨테이너 시작 순서인데, Pending은 1단계 스케줄링 실패로 배치된 노드 자체가 없어 pull조차 발생하지 않은 상태이고, ErrImagePull은 배치는 성공했지만 2단계에서 이미지를 레지스트리에서 가져오지 못한 상태입니다. 전자는 requests/노드 자원을, 후자는 이미지 이름과 레지스트리 접근을 확인해야 합니다."
